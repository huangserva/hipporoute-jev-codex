# 2026-09-19 真实 Jev 端到端验证

一句话结论：真实 Jev 已能把机械任务路由到 luna、把复杂主任务和子 agent 路由到 astra，且 `response.completed.model` 与路由决定一致；线程钉住、工具续跑不问 Jev、子线程独立决策和新轮次算账关卡均生效，但这次单样本中真路由因产生更多调用和 token，估算费用反而比纯 astra shadow 高约 19.8%。

## 实验条件

- Codex CLI：0.155.1。
- 路由器上游：直连 `https://chatgpt.com/backend-api/codex`。
- 网络：系统 `HTTPS_PROXY=127.0.0.1:7897`，路由器经代理 CONNECT 转发。
- Jev key：仅由 `~/.jev.env` 的 `TYPESAFE_API_KEY` 加载；`GET /health` 返回 `jev_key: true`，实验和报告均未输出 key。
- 两轮使用同一组任务描述：第一用户轮次是查找并建议重命名 `stay_cost` 的机械任务；第二用户轮次分析 `switch_gate` 边界条件，并派生一个原生子 agent 独立审计。
- 第一轮开启 shadow，所有请求实际由 `gpt-6-astra@medium` 服务；第二轮关闭 shadow，实际应用 Jev 路由。
- 原始决策和 Codex JSONL 保存在被 `.gitignore` 排除的 `runtime/`。日志里的 `task` 最多 160 字符，并对常见 key/token 形态做替换脱敏。

## 第一轮：shadow

三个真正的路由决策均为 `apply`，没有 `no_key`。非决策请求按设计记录为 `sticky`。

| 决策点 | Jev 想选（`would`） | 实际服务 | SSE `response.completed.model` | Jev 耗时 | 人工判断 |
|---|---|---|---|---:|---|
| 主线程首请求：机械改名 | `luna@max` | `astra@medium` | `gpt-6-astra` | 1106 ms | luna 合理，任务机械且边界明确 |
| 主线程第二用户轮次：边界分析 | `astra@high` | `astra@medium` | `gpt-6-astra` | 689 ms | astra/high 合理，需要代码审计与多边界推理 |
| 子 agent 首请求：独立审计 | `astra@high` | `astra@medium` | `gpt-6-astra` | 2112 ms | astra/high 合理，委托任务仍是复杂审计 |

shadow 轮共有 22 次模型请求、2 个 thread id：`first_request ×1`、`new_user_turn ×1`、`subagent_first ×1`、`tool_continuation ×16`、`reuse ×3`。19 次续跑/复用均为 `sticky`、`consulted_jev=false`；22 个完整 SSE 的上游 model 都是 astra。

第二用户轮次从线程策略状态里的 luna 切到 astra，关卡数据为：

差额约 `$0.221932`，未超过 `$0.25`，所以没有出现 `hold`。

## 模型真实切换的硬证据

真路由的三个决策请求都在上游 SSE 的 `response.completed.response.model` 中给出了模型，逐条等于路由器决定：

```jsonl
{"event":"first_request","model":"gpt-5.6-luna","upstream_model":"gpt-5.6-luna","gate":"apply"}
{"event":"new_user_turn","model":"gpt-6-astra","upstream_model":"gpt-6-astra","gate":"apply"}
{"event":"subagent_first","model":"gpt-6-astra","upstream_model":"gpt-6-astra","gate":"apply"}
```

因此证据不仅是路由器改写了请求：ChatGPT Codex 后端完成事件也确认机械任务由 luna 服务，复杂主任务和子 agent 由 astra 服务。

24 条真路由日志中，23 条包含 `response.completed`，其 `upstream_model` 全部与路由决定一致；另有 1 条 HTTP 200 工具续跑流没有观察到 `response.completed`，model 和 usage 均为空。这条不计入模型一致性和费用硬证据，见“发现与修复”。

## 用量与单次费用对比

计算采用 `BACKTEST.md` 的每百万 token 价格：

```text
费用 = (input_tokens - cached_tokens) × input_price
     + cached_tokens × cached_input_price
     + output_tokens × output_price
```

再除以 1,000,000。本次响应的 cache-write token 为 0；汇总的是每次 `response.completed` usage，因此包含多次工具调用反复携带上下文产生的计费 token。

| 模式 | input_tokens | cached_tokens | output_tokens | 估算费用 |
|---|---:|---:|---:|---:|
| shadow，全部 astra | 605,234 | 546,688 | 5,460 | `$1.405148` |
| 真路由，luna + astra | 718,092 | 622,592 | 7,650 | `$1.682868`（下界） |

真路由分模型：

| 真实模型 | input | cached | output | 估算费用 |
|---|---:|---:|---:|---:|
| luna | 52,658 | 33,280 | 1,121 | `$0.005886` |
| astra | 665,434 | 589,312 | 6,529 | `$1.676982` |

真路由的已观测费用比 shadow 高 `$0.277720`，约 `19.8%`；input、cached、output 分别多约 `18.6%`、`13.9%`、`40.1%`。原因不是 luna 单价更贵，而是两次非确定性 Agent 执行走出了不同轨迹：真路由有 24 次请求，shadow 有 22 次，且复杂轮次的输出和上下文更大。还有一条真路由流缺 completed usage，因此 `$1.682868` 只是下界。

这是同任务集各跑一次的单次样本，不能据此判断路由长期省钱或费钱。后续应固定工具轨迹或扩大样本，并分别报告“同 token 价格收益”和“模型改变行为后产生的 token 变化”。

## Jev 延迟

| 模式 | 三次决策耗时 | 平均 | 中位数 | 范围 |
|---|---|---:|---:|---:|
| shadow | 1106 / 689 / 2112 ms | 1302 ms | 1106 ms | 689–2112 ms |
| 真路由 | 812 / 1892 / 1366 ms | 1357 ms | 1366 ms | 812–1892 ms |
| 合计 | 六次 | 1330 ms | 1236 ms | 689–2112 ms |

本次六次调用都低于 4 秒，没有触发超时重试。用户在本实验前的直接调用曾观察到首次调用约 6.7 秒：第一次超过 4 秒，重试才成功；后两次约 1.4–2.2 秒。结合本机 HTTPS 代理，冷启动或首次建连延迟必须纳入生产监控，不能只看热路径的约 0.7–2.1 秒。

## 发现与修复

1. **真实验证所需观测字段不足。** 原实现的 health 看不出 key 是否加载，日志没有 Jev 耗时、真实 completed model、output token，也把 shadow 覆盖成模糊的 `gate=shadow`。已增加 `jev_key` 布尔、`jev_ms`、`upstream_model`、完整 usage、`shadow`、`reason` 和脱敏 task；策略决定使用 `apply/hold`，shadow 另用布尔字段表示。
2. **预算等号存在浮点误拒。** 已复现 `1.0 - 0.7 = 0.30000000000000004` 导致数学上等于 `$0.3` 的切换被拒。已改用 `Decimal(str(...))` 做金额比较，并补回归测试。
3. **未知模型或缺失价格会抛 `KeyError`，最终可能成为 HTTP 502。** 已改成安全 `hold`，reason 分别为 `unknown_model` / `missing_price`，成本记为未计算，并补测试。
4. **一个 HTTP 200 SSE 没有可观察的 `response.completed`。** 现有证据无法区分是上游未发、连接被提前结束，还是未识别的终止事件；Codex 随后继续完成会话。已新增 `response_completed` 日志布尔，后续复现时可直接检索，但本次丢失的 model/usage 无法补算。
5. **同模型只改 effort 会按缓存重建收费。** 这是阶段一既定且已有测试覆盖的保守假设，不作为本次 bug 修改；需要用后端缓存命中实测决定阶段二是否放宽。

修复后离线测试总数为 50 项。
