# T1–T4 结论落地与常驻健壮性

一句话结论：T3 的 `luna@low` 已成为默认值，T4 暴露的纯协调父线程通过 Jev 分类说明加 `coordination_hint` 后，s2 三次 raw Luna 置信度从 0.26–0.31 提升到 0.98–0.99 且全部通过；评审 B3/B6/B7 也已分别以后台状态刷新、HTTP 资源边界和上游首块嗅探修复。

## 结论如何落进代码

### T1 与 T2

- T1 决定不强制 `fork_turns=none`：已有子 agent 生命周期和继承方式保持不变，仍由每个子线程首请求独立分档。
- T2 的“下游断开仍排空上游”修复保持不变；本轮 s2 有效请求全部收到 `response.completed`，真实模型证据完整。

### T3：Luna 默认 effort 改为 low

- `config.py`、`config.example.toml` 和基准配置生成器的默认值由 `max` 改为 `low`。
- `candidate_from_jev` 的独立默认参数同步为 `low`，避免不经配置调用时漂移。
- README 与 STATUS 明确：可用 `[routing] luna_effort = "medium"` 或 `"max"` 覆盖，`service_tier=priority` 不变。
- 原因来自 T3 的 54 个有效机械任务会话：三档均 100% 通过，low 相对 max 请求数中位数少 41.7%、墙钟少 44.6%、费用中位数少 40.3%。

### T4：纯协调父线程单独提示

采用两层信号，但不在路由器里硬编码 Luna：

1. Jev tier instructions 明确说明：只负责委托子任务并汇总结果、不亲自执行实际工作的协调型任务属于 Luna，即使子任务跨多个模块。
2. 父线程 task 同时出现“子 agent”“并行/派发”“等待/汇总”三类显式语义时，Jev state 顶层和 `signals` 都增加 `coordination_hint=fanout_coordinator`。子线程不设置该 hint，仍只评估自己的委托任务。

最终模型仍由 Jev raw choice、0.5 置信度门槛和既有 fail-open 规则决定；协调检测只是提示，不绕过门槛。

## s2 父线程前后对比

前组取自 `runtime/bench/t4-full-20260920/` 的 0.5 门槛三次有效 s2；后组使用当前同一代码版本、`luna@low`、门槛仍为 0.5，命令为：

```bash
python3 -u bench/run_subagent.py \
  --task-ids s2_parallel_tests --modes live --repeats 3 \
  --run-id s2-coordination-20260921 --port 4333
```

| 指标 | 修改前 T4 | 修改后复验 |
|---|---:|---:|
| 父线程 raw Jev | Luna 0.26 / 0.27 / 0.31 | Luna 0.99 / 0.98 / 0.99 |
| 门槛后父模型 | Sol / Sol / Sol | Luna / Luna / Luna |
| completed 真实父模型 | Sol（全部请求） | Luna（11 / 9 / 13 请求） |
| 父线程 effort | Jev depth | low / low / low |
| 父线程费用中位数 | $0.237744 | $0.008326（低 96.5%） |
| 会话总费用中位数 | $0.246510 | $0.019020（低 92.3%） |
| 墙钟中位数 | 150.5s | 106.9s（低 29.0%） |
| 父线程请求数中位数 | 14 | 11 |
| 自动通过率 | 3/3 | 3/3 |

修改后三次所有父/子线程的 `response.completed.model` 都与策略模型一致，没有缺 completed。Jev 调用耗时分别为 2073、2884、5817ms；第三次超过单次 4 秒，说明重试/冷延迟仍存在。

共有一次额外尝试被排除：第二遍第一次执行时 `test_policy` 子线程 Jev `URLError`，按设计 fail-open Astra，驱动标为基础设施失败并重跑；父线程当次仍为 Luna 0.99。这不是协调分类失败。

限制：前后两组是独立 Jev/Agent 轨迹，且本轮同时采用了 T3 的 Luna low 默认，所以费用与墙钟差不能全部归因于 coordination hint；本轮也没有做 instructions-only 与 hint-only 消融。能够硬证明的是：相同 s2 提示在当前组合方案下，父线程三次置信度都越过 0.5、真实走 Luna，且通过率未下降。

## 常驻健壮性修复

| 评审项 | 修改 | 测试证据 |
|---|---|---|
| B6 请求资源边界 | 默认 16 MiB 请求体；Content-Length 和 chunked 累积都返回 413；socket timeout 30s；64 路 POST 并发，超限 503 并记录 `gate=server_busy` | 超长定长/chunked、timeout 注入、信号量耗尽与拒绝日志测试 |
| B7 Content-Type 缺失 | 200 且无 Content-Type 时增量预读最多 64 字节；仅 `event:`/`data:` 判 SSE，否则按 JSON；预读块继续进入 capture/tracker/relay | 200+JSON 流式调用方保持 JSON；`event:` 跨 read chunk 仍识别；既有无类型 SSE 字节精确透传和非流式组装继续通过 |
| B3 状态落盘 | 更新只改内存并递增 dirty generation；后台默认 2s 合并原子写，I/O 不持状态锁；退出强制 flush | 无同步写、三次更新一次 flush、后台周期落盘、close 幂等强刷、server_close 调 close |

B3 用 generation 而不是单布尔 dirty：若快照写盘期间又有更新，写完只确认旧 generation，新更新仍保持待刷，避免并发更新静默丢失。

## 仍需注意

- 协调识别只覆盖明确措辞；隐式协调、嵌套协调或父线程还要亲自做复杂工作的混合任务仍需扩大样本。
- 状态后台刷新减少关键路径 I/O，但没有替代 schema 迁移、日志轮转、磁盘满恢复和崩溃测试。
- HTTP 资源上限解决了无界线程/请求体风险，但本机服务仍无鉴权；常驻前仍应实现 B10/B11、服务托管与 soak test，详见 STATUS。
