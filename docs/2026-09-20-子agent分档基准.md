# 子 agent 分档基准（2026-09-20）

**一句话结论：**在 Codex CLI 0.155.1 的 24 个有效 fan-out 会话中，子线程首请求独立分档后 24/24 任务通过，已完成 SSE 的子 agent 费用相对全 astra 的 shadow 样本降低 **83.90%**，父子合计降低 **79.74%**；但 live 总墙钟高 21.5%，且 live 有 18 条流缺 `response.completed`，因此费用数是下界，不能把这一次小样本当成生产收益结论。

## 先验证：委托文本在边界上可见吗

用真实 `spawn_agent` 和临时反向代理抓取了 Codex 到 Responses 后端的完整请求，原始文件保留在 Git 忽略的 `runtime/phase2-capture/`。下面是脱敏后的真实片段。

子线程首请求中，`NEW_TASK` 的任务名、发送者和结构是明文，但 payload 本身是独立的密文 content part：

```json
{
  "type": "agent_message",
  "author": "/root",
  "recipient": "/root/delegation_probe",
  "content": [
    {"type":"input_text","text":"Message Type: NEW_TASK\nTask name: /root/delegation_probe\nSender: /root\nPayload:\n"},
    {"type":"encrypted_content","encrypted_content":"[encrypted 292 chars]"}
  ]
}
```

父线程后续请求中保留了 `spawn_agent` function call，但只有 `task_name` 和 `fork_turns` 是明文，`message` 在进入边界代理之前已加密：

```json
{
  "type": "function_call",
  "name": "spawn_agent",
  "arguments": {
    "task_name": "delegation_probe",
    "fork_turns": "all",
    "message": "[encrypted 292 chars]"
  }
}
```

额外抓取了上游 SSE：`response.output_item.done` 里的 spawn arguments 也已是相同密文，本地 Codex rollout 没有可供路由器使用的明文副本。所以，**Codex 0.155.1 的 Responses 边界上无法还原具体委托 payload**。

实现不猜测、不尝试解密，而是按以下优先级选 Jev task：

1. 未来版本若在 `NEW_TASK Payload` 中出现明文，直接使用；
2. 未来版本若父线程 spawn arguments 出现明文，按 `parent_thread_id + agent_name` 缓存后使用；
3. 当前版本使用 `agent_name/task_name + 明确标注的父任务上下文`，并记 `delegation_source=agent_name_fallback`。

阶段一的猜测也被证实：子线程请求会继承父线程原始用户提示，旧 `inspect_request` 因此会把父任务错当成子任务。现在子线程使用上述专用 routing task，而不是继承父线程的模型或普通 task 提取结果。

## 实现与安全性

- 子 agent 首请求独立调 Jev；state 和日志增加 `parent_tier`、`agent_name`、`subagent_kind`、`delegation_source`和 `parent_thread_id`。
- Jev 的 tier/depth instructions 明确要求只评估被委托的子任务，`parent_tier` 只是背景，不是默认答案。
- 同一 thread id 的“读状态—决策—写状态”由 per-thread lock 串行化；并发首请求的单测证明只调用一次 Jev。
- 状态按 `last_active_at` 做保守 TTL/GC，默认 24 小时；无法解析时间戳的旧状态不删除。
- 正式样本中 90 个线程恰好发生 90 次 Jev 决策（24 父 + 66 子）；522 次 `tool_continuation` 和 84 次 `reuse` 全部 `consulted_jev=false`。

## 基准设计

`bench/tasks-subagent.json` 定义了 4 个可自动验收的 fan-out 任务：

| ID | fan-out | 子任务 |
|---|---:|---|
| s1_parallel_docstrings | 3 | 给 policy/sse/upstream 的指定函数各补一条 docstring |
| s2_parallel_tests | 3 | 分别跑 policy/jev/config 单测，父 agent 汇总 JSON |
| s3_parallel_typos | 2 | 分别修正 README 和 STATUS 的预置错字 |
| s4_mixed_fanout | 3 | docstring、Jev 单测、GC 边界审计三种混合子任务 |

每个样本都在 `runtime/bench-work/` 的全新临时副本中运行，每任务是独立 `codex exec` 新会话。shadow 与 live 顺序交替，每格 3 遍，共 24 个有效会话。shadow 仍调 Jev 并记 `would`，实际全部服务 astra@medium；live 应用 Jev 分档。费用按 `BACKTEST.md` 中 input/cached input/output 价格从 `response.completed.usage` 逐请求计算。

## 真实模型的硬证据

模型证据只取上游 SSE `response.completed.response.model`，不以路由器的预期字段代替：

- shadow：275 条有 completed 的请求全部返回 `gpt-6-astra`。
- live：401 条有 completed 的请求中，292 条返回 `gpt-5.6-luna`，109 条返回 `gpt-5.6-sol`，0 条 astra；每个线程的 completed model 都与该线程钉住的 policy model 一致。
- 例如 s4/live 第 1 遍，父线程是 sol，`audit_gc_edges` 是 sol，低置信度的 `config_docstring` 回退 sol，`run_jev_tests` 是 luna；四个线程的所有 completed model 均与此一致。

缺 completed 的流没有被静默丢弃：原始数据在每个 thread 上记了 `missing_completed` 和 `cost_is_lower_bound`。共 20 条，全部发生在父线程（shadow 2、live 18），子线程是 0。这些流无 usage 可计价，所以两轮费用都是下界，且 live 的低估更明显。

## 墙钟、失败与清理

12 个有效 live 样本总墙钟 1728.3s，shadow 为 1421.9s。live 多发出了 142 次请求（419 vs 277），输出 token 也更多；当前数据不能把墙钟差异单独归因于 Jev 延迟或模型速度。

实际共执行 25 次 attempt：`s3_parallel_typos/live/repeat-3` 的第一次在 1200.0s 超时，驱动依规记录后重跑，第二次 107.4s 通过。汇总只使用有效重跑，失败 attempt 保留在 `attempts.jsonl`。

运行结束后：

- `~/.codex/config.toml` SHA-256 恢复为运行前的 `<redacted-sha256>`；
- 4320 端口无监听路由器；
- shadow/off 哨兵文件均已删除；
- `runtime/bench-work/` 工作副本已清空；
- Jev key 未写入报告、决策日志或 Git。

## 这个结果能说明什么，不能说明什么

能说明：

- 父线程和每个原生 collab-spawn 子线程能独立决策、独立钉住，工具续跑不重问 Jev。
- 在这 4 类受控 Python 任务上，将明确机械子任务从 astra 下放到 luna/sol，自动验收质量未下降，已完成 SSE 的计价显著降低。
- 0.5 置信度门槛会把 Jev “选 luna 但不够确定”的子任务保守提到 sol，实测确实发生了这条路径。

不能说明：

- 不能证明 79.74% 是普适收益；样本只有 4 个任务、3 次重复，且 missing completed 对 live 的费用低估更多。
- 不能证明人工质量等价；通过条件只检查文件内容和命令退出码。
- 没有覆盖 fork、嵌套子 agent、自定义 `~/.codex/agents/`、路由器重启恢复或 Codex Router caller edge。
- 当前边界只能用 agent name 作委托语义的代理特征；如果上层给出“worker1”之类无语义名称，Jev 看不到加密 payload，分档质量会下降。这是 Codex 0.155.1 协议的核心限制。
