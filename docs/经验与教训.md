# HippoRoute-Jev-Codex：项目经验与全部测试记录

> 本文汇总 2026-09-19 至 09-21 的全部实验、结论、走过的弯路和方法论。
> 所有数字来自真实 Codex 会话，模型切换以上游 SSE `response.completed.response.model` 为准。
> 样本规模是单机单用户，不构成普适保证。

---

## 一句话结论

在 Codex 上，LLM 路由的收益**只存在于线程边界**：新会话首请求、子 agent 首请求。
机械任务省 80% 到 95%，代价是墙钟多两到三成，调低便宜模型的思考深度后能收回大半。
**工具循环内换模型必亏，压缩点上精简历史在 Codex 上机制不通。**

---

## 一、项目由来

起点是一个反直觉的实测结果：按原作者 `jev-codex-router` 的做法，**每个请求都问一次路由模型**，结果 token 消耗反而更高。

原因不在路由模型判断不准，而在 prompt cache：

- 缓存按前缀匹配，且**按模型隔离**。
- 中途换模型 = 整段历史在新模型上重新写入缓存，按 cache-write 价（约 input 的 2 倍）计费。
- 反直觉的价格倒挂：顶配模型的**缓存读**单价，可能低于便宜模型的**冷输入**单价。缓存命中率越高，换便宜模型越亏。

三方证据互相印证：

| 来源 | 证据 |
|---|---|
| 本项目实测 | 逐步路由 token 反增 |
| `jcm-router` 作者 | 路由主对话 309 次请求净亏 $19.53，日志里 `cache_read=0` / `cache_creation=360k` |
| 行业分析 | 缓存命中率超过 94.8% 时，从热的顶配切到冷的便宜模型必然更贵 |
| OpenRouter | 会话建立后锁定模型，官方文档理由就是保护缓存 |

于是本项目的第一性原则确定为：**模型和思考深度只在缓存前缀反正要重建的时刻更换。**

## 二、测试全记录

### 前置验证：Codex 请求里有没有线程标识

不做实现，先抓包。自建反向代理抓取 15 个真实请求。

| 用途 | 字段 | 行为 |
|---|---|---|
| 线程主键 | header `thread-id` | 主线程与每个子 agent 各不同，跨用户轮次稳定 |
| 根会话 | header `session-id` | 主线程与子线程共享 |
| 用户轮次 | `x-codex-turn-metadata.turn_id` | 一轮内工具续跑不变，新轮次才变 |
| 子 agent | `x-openai-subagent: collab_spawn`、`x-codex-parent-thread-id` | 三个冗余来源 |
| **不能用** | `prompt_cache_key` | 主线程与子线程相同，只表达缓存域 |
| **不能用** | instructions + 首条用户消息哈希 | 两个不同子线程会碰撞 |

最后那条是兜底方案的证伪：如果不抓包直接实现，这个"看起来合理"的方案会让所有子线程共用一个状态。

### 实验 1：首次真实端到端

机制全部跑通，上游返回的模型与路由决定逐条一致。但**费用比全顶配高 19.8%**。

拆开看两个原因：任务集以推理任务为主，便宜档只服务了 24 次请求里的 3 次；以及会话中途从便宜档升级到顶配，要在顶配上冷读 18k 上下文，单次切换成本 $0.229，占两轮总差额 $0.278 的大头。

**教训**：第一次跑通不等于有收益。条件不对，机制再对也省不到钱。

### 实验 2：机械任务基准（48 个全新会话）

针对上一次的两个失败原因重新设计：6 个机械任务 + 2 个推理任务，每个任务一个全新会话，只在开头选一次模型。

| 分组 | 全顶配 | 真路由 | 差 | 通过率 |
|---|---:|---:|---:|---:|
| 机械任务，各 18 次 | $5.79 | $0.27 | **省 95.4%** | 两边 100% |
| 推理任务，各 6 次 | $5.82 | $6.15 | 多 5.6% | 两边 100% |
| 全部 | $11.62 | $6.42 | **省 44.8%** | 两边 100% |

上游模型硬证据：便宜档 292 次、中档 109 次、顶配 0 次。

代价：墙钟中位数 54.2 秒涨到 97.6 秒。

### 实验 3：子 agent 分档（24 个 fan-out 会话）

| 分组 | 全顶配 | 真路由 | 差 |
|---|---:|---:|---:|
| 父线程 | $6.34 | $1.60 | 省 74.8% |
| 子线程 | $7.51 | $1.21 | **省 83.9%** |
| 合计 | $13.85 | $2.81 | 省 79.7% |

90 个线程恰好 90 次路由决策，522 次工具续跑全部沿用钉住的模型，一次都没问。

**发现一个协议硬限制**：委托内容在 Responses 边界上是加密的。父线程 spawn 的 `message` 参数和子线程收到的 `NEW_TASK` payload 都是密文，路由器只能用 agent 名加父线程上下文做判断依据。任务名有语义就判得准，上层若用 `worker1` 这种名字质量会掉。

### 实验 4（T1）：长父线程 fan-out（27 个会话）

回答"父线程变长以后，子 agent 换模型是否变亏"。

| 父上下文 | 全顶配 | 真路由 | 子 agent 首请求 |
|---:|---:|---:|---:|
| 31k | $1.56 | $0.064 | 22.3k |
| 75k | $2.94 | $0.086 | 22.4k |
| 149k | $5.90 | $0.158 | 22.6k |

**结论出乎预期**：`fork_turns=all` 并没有把父线程历史全量复制给子 agent。父上下文涨了 5 倍，子 agent 首请求几乎不动。所测范围内没有出现费用交叉点。

强制 `fork_turns=none` 能把首请求降到 16.9k，通过率不掉，但整线程费用没有稳定优势（三档分别是低 12%、持平、高 3%）。

**决定**：保留默认继承，不安装强制不继承的钩子。

**局限**：这次的长上下文全由工具输出构成，很可能正是 fork 不继承的部分。用户消息或父 agent 文本构成的长上下文未测。

### 实验 5（T2）：缺失完成事件排查

子 agent 基准里有 18 条流没有 `response.completed`，费用只能算下界。

抓原始字节流后分类，排除了"上游没发""解析器丢数据""终止事件换了类型"，**根因是客户端中途断开后路由器立刻关闭上游连接**，后面的完成事件没读到。

修法：下游断开就停止写客户端，但继续把上游读到底。修复后同任务 6 次共 127 个请求，缺失归零；其中 14 次客户端断开，全部在断开后读到了完成事件。

### 实验 6（T3）：便宜档的思考深度（54 个会话）

原作者的规则是"便宜档永远用最高思考深度"，理由是它便宜。实测这条规则在机械任务上是错的。

| 思考深度 | 通过率 | 每会话请求数 | 墙钟中位数 | 费用中位数 |
|---|---:|---:|---:|---:|
| max（原默认） | 18/18 | 12 | 112 秒 | $0.0116 |
| medium | 18/18 | 9 | 76 秒 | $0.0083 |
| **low** | 18/18 | **7** | **62 秒** | **$0.0069** |

改善来自两头：步数少 42%，每步输出也少 38%。便宜模型在最高深度下不是"想得更周全"，而是"多绕了路"。

**决定**：默认改为 low，保留配置项。

### 实验 7（T4）：置信度门槛（24 个会话）

| 门槛 | 通过率 | 被改成贵档的回退 | 总费用 |
|---|---:|---:|---:|
| 0.5（默认） | 12/12 | 4 次 | $2.79 |
| 0.35 | 12/12 | 0 次 | $2.55 |

看起来降门槛更好，但拆开看：4 次昂贵回退里只有 1 次落在 0.35 到 0.5 之间，另外 3 次置信度只有 0.26 到 0.31，降到 0.35 照样回退。

**真正的问题不是门槛，是任务类型**：那 3 次全是"父 agent 只负责派活和汇总"的协调型任务，路由模型对这类任务的置信度系统性偏低。

**决定**：门槛不动，单独处理协调型任务。

### 实验 8：协调型父线程修复验证

两层信号：在路由模型的问题说明里明确"只委托和汇总、不亲自执行的协调任务归便宜档"，并在父线程提示同时出现子 agent、并行、汇总语义时附加协调提示。

| 指标 | 改前 | 改后 |
|---|---:|---:|
| 父线程置信度 | 0.26 / 0.27 / 0.31 | 0.99 / 0.98 / 0.99 |
| 父线程实际模型 | 贵档 × 3 | 便宜档 × 3 |
| 父线程费用中位数 | $0.238 | $0.008 |
| 会话总费用中位数 | $0.247 | $0.019 |
| 通过率 | 3/3 | 3/3 |

### 实验 9：压缩点上精简历史（Codex 上不可行）

在 Claude Code 上，插件可以直接替换压缩后的历史，省下写摘要那次调用。**Codex 不行**：

- 压缩在服务端完成，返回一个加密检查点，**大小固定约 102k，本地既换不掉也没法让它变小**。
- 本地唯一能碰的是压缩请求的输入，而删除旧的工具输出会让它后面的所有内容前缀失配，全部按未命中重算。

6 次运行的结果：

| 做法 | 压缩那次的输入 | 其中命中缓存 | 总计中位数 | 相对原生 |
|---|---:|---:|---:|---:|
| 原生压缩 | 109k | 88k | 26.6 | 基准 |
| 规则删旧输出后压缩 | 88k | 45k | 28.6 | 多 8% |
| 路由模型挑着删后压缩 | 99k | 67k | 25.1 | 少 6%（噪音） |

删得越多，压缩那一次越贵（规则组多付 44%，模型组多付 22%）。

社区的三个 Codex 移植版也印证了这一点，作者们自己的说明：一个写"不宣称减少实时 token"，一个在 README 开头写"我不推荐使用这个"，一个写"Codex 目前没有暴露替换内置压缩结果的钩子"。

**结论**：这条路在 Codex 上关闭。有收益的只有路由那一半。

## 三、独立代码评审发现的问题

由另一个 agent 只读评审，发现 5 条会导致错误路由或损坏请求的问题、12 条生产环境会踩到的问题。其中两条最有价值：

### 压缩判定的常量在真实 Codex 里根本不存在

判定压缩请求的方式是匹配提示词开头，这句话是从原作者项目抄来的。实测在两个 Codex 二进制里搜索，**该字符串出现 0 次**，真实提示词完全不同。

更要命的是：**测试用的输入就是这个常量本身**，所以测试与实现共享同一个错误假设，永远发现不了脱节。

修法：改用请求元数据判定（`request_kind=compaction` 加结构化字段），并用一次真实压缩的抓包做测试样本。

> **这是本项目最有价值的一条教训：涉及外部协议字面量的判定，必须用真实抓包固化的样本来测，不能用自己定义的常量测自己。**

### 同模型改思考深度被当成缓存重建计费

成本函数不区分"换模型"和"只改思考深度"，一律按目标模型的缓存写入价计算。但改思考深度不改前缀，缓存照样命中。结果是上下文超过约 5.4 万 token 后，任何加深思考的请求都被预算挡回，正好锁死在最需要深度的长任务上。这个错误同样被一条测试固化成了断言。

## 四、真实使用中发现的问题（尚未解决）

接入真实工作流后立刻暴露一个设计缺陷：**成本关卡在长对话里挡掉所有降级**。

真实追问场景，上下文 66k 和 70k：

```
留守成本 $0.0013（顶配缓存读）
切换成本 $0.3336（便宜档缓存写）
差额 $0.33 > 预算 $0.25  →  拒绝切换
```

问题在于这个公式**只看这一次的切换成本，不看后续每一轮用便宜模型的收益**。便宜档单价是顶配的五十分之一，就算真的重写一遍缓存，两三轮就回本。

待改方案：预算从固定金额改为"切换成本要能在 N 轮内回本"，或降级时按目标模型单价缩放预算。改完必须重新验证。

## 五、方法论经验

这些比具体数字更可复用。

**先验证再实现。** 每个阶段都先抓包确认协议事实，再写代码。线程标识、子 agent 标识、压缩请求形状、委托内容是否加密，全部是先有证据再有实现。省下的返工远大于抓包成本。

**影子模式是免费的真实数据。** 照常做决策并记录"本该选什么"，实际不改变任何行为。质量中性，可以在生产环境长期开着校准参数。

**硬证据要来自对方，不能来自自己。** 所有"模型真的切换了"的结论，依据都是上游返回的 `response.completed.response.model`，而不是路由器改写了请求字段。前者是对方确认，后者只是自己的意图。

**每份报告必须写"不能说明什么"。** 样本量、任务分布、非配对轨迹、缺失数据，全部显式列出。这一条让多次"看起来很好"的结果没有被过度解读，例如 T4 的 8.5% 省钱其实只有 1 个样本能归因于参数变化。

**区分基础设施失败和任务失败。** 网络错误、超时、配额耗尽要单独记录并重跑，不能混进有效样本，也不能静默丢弃。两轮测试里出现了 8 次路由模型的网络错误，如果混进去会污染结论。

**独立评审能发现作者看不见的问题。** 压缩判定常量脱节、自指测试、成本模型错误，都是作者本人反复读代码也不会注意到的，因为它们符合作者自己的假设。

**抄别人的常量要验证。** 从参考项目抄来的提示词、阈值、规则，都要在自己的环境里验证一遍。本项目抄了三样，两样是对的（流式处理细节、失败回退方向），一样是错的（压缩判定），还有一样是过时的（便宜档永远最高思考深度）。

## 七、仍未解决 / 未覆盖

- **成本关卡在长对话里挡掉降级**（第四节），真实使用中已发生，必须改。
- **推理任务是否真的更贵**，样本只有 6 次，方向和量都不确定。
- **时间代价**，最优配置下仍比全顶配慢约 12 秒。
- **路由模型的网络稳定性**，两轮测试共出现 8 次网络错误触发回退。
- **长上下文由用户消息或模型文本构成时**，子 agent 的 fork 行为未测。
- **嵌套子 agent、自定义 agent 定义、崩溃恢复、长跑压力**，全部未覆盖。
- **生产常驻**还缺本地鉴权、日志轮转、soak 测试。

## 附：与参考项目的关系

本项目借鉴了 `jev-codex-router`（0xNatoshi）的流式转发细节、边界通道的已知约束和失败回退思路，遵守其 MIT 许可。核心差异是决策时机：参考项目每个请求都路由，本项目只在四个边界路由，其余请求沿用线程已钉住的选择。

同时参考了 `jcm-router` 的切换成本模型、`jev-router` 的上下文阈值规则、`jevcoder` 的"只追加不改前缀"控制消息设计、`pi-jev-harness` 的前瞻式裁剪问题设计。

本项目与 OpenAI、TypeSafe 无关。
