# T1：长父线程 fan-out 基准（2026-09-20）

**一句话结论：**在这组由文件工具输出累积出 31k/75k/151k 父上下文的样本里，`fork_turns=all` 子 agent 首请求始终只有约 22.3k，没有随父上下文线性增长；强制 `none` 能再降到约 16.9k，但 27/27 都通过时它对整会话费用没有稳定优势。所测三档中 `live_all` 都远低于 shadow，**没有出现不如 shadow 的交叉点，不建议现在强制 `fork_turns=none`**。

## 设计

父 agent 按顺序逐个读取 `runtime/bench-fixtures/` 中确定性生成的文本文件，每个 fixture 约 24,000 字节。读完后在同一轮并行 spawn 三个机械子任务：分别给 `inspect_request`、`assemble_sse`、`UpstreamClient.open_response` 补 docstring，并运行相关单测。父线程真实上下文取“第一个子请求开始之前，父线程最后一个 `response.completed.usage.input_tokens`”，不用字符估算。

三个档位：

| 名义目标 | fixture 数 | 27 样本中实际父上下文中位数范围 |
|---|---:|---:|
| 30k | 2 | 30,797–34,398 |
| 80k | 10 | 71,685–77,287 |
| 150k | 24 | 149,008–156,247 |

三种设置：

- `shadow_all`：Jev 记 `would`，父子实际全部 astra@medium，spawn 显式 `fork_turns=all`；
- `live_all`：路由器实际分档，spawn 显式 `fork_turns=all`；
- `live_none`：路由器实际分档，临时工作副本的 PreToolUse 钩子将 spawn `fork_turns` 改为 `none`。

钩子 matcher 是 `.*spawn_agent`，实际工具名为 `collaborationspawn_agent`；脚本保留原 `tool_input` 的所有字段，只改 `fork_turns`，不改 model/effort。`codex exec` 仅在该设置加 `--dangerously-bypass-hook-trust`。钩子只在临时 benchmark workspace 中，每次会话后随 workspace 删除。

三档 × 三设置 × 三遍，共 27 个有效新会话；设置顺序在档位和重复间旋转。原始数据位于 Git 忽略的 `runtime/bench/t1-long-parent-final-20260920/`。

## 三个问题的直接答案

### 1. `live_all` 的子首请求会随父上下文增长吗

没有。父上下文中位数从 31.3k 增到 75.2k 再到 149.0k，子首请求仅从 22,342 变到 22,449 和 22,636，增幅约 1.3%。首请求缓存命中率中位数是 95.10% / 71.83% / 98.18%，非单调；各档中第一个启动的 `docstring_policy` 中位命中率为 63.03% / 62.72% / 62.21%，也几乎不变。

子线程费用中位数反而从 $0.034727 降到 $0.027847/$0.027685，没有父历史冷读随上下文增长的证据。总费用从 $0.063925 增到 $0.085624/$0.158447，增量来自父线程自身读更长上下文，不是三个子线程各自重读 80k/150k。

这表明 Codex 0.155.1 的 `fork_turns=all` **不会将本实验中由工具输出构成的全部父历史复制进子 agent 请求**。它仍比 none 多约 5.6k input，说明会继承一部分固定历史/上下文，但不与本次文件输出累积量成比例。

### 2. `live_none` 是否消除冷读，通过率是否下降

`none` 将子首 input 稳定降到约 16.85k，相对 all 少 24.5%–25.5%，所以钩子确实去掉了 all 继承的固定部分。但 all 本来就没有重读 30k/80k/150k 的工具历史，因此 none 没有“消除随父上下文增长的冷读”可做。

通过率：`live_none` 9/9 会话、27/27 子任务验收通过，和 `live_all` 一样。但费用不稳定更低：

| 档位 | none 相对 all，总费用 | none 相对 all，子费用 |
|---|---:|---:|
| 30k | 低 12.33% | 低 14.68% |
| 80k | **高 0.44%** | **高 43.64%** |
| 150k | 低 2.90% | **高 11.35%** |

这些差异与 luna 执行步数、输出 token 和后续缓存复用的波动同量级，不足以支持全局强制 none。

### 3. `live_all` 在哪个父上下文档开始不如 shadow

**所测范围内没有交叉点。**

| 档位 | shadow 总费用中位数 | live_all 总费用中位数 | live_all 节省 | shadow 子费用 | live_all 子费用 | 子费用节省 |
|---|---:|---:|---:|---:|---:|---:|
| 30k | $1.557150 | $0.063925* | 95.89% | $0.835224 | $0.034727 | 95.84% |
| 80k | $2.941972 | $0.085624 | 97.09% | $0.842262 | $0.027847 | 96.69% |
| 150k | $5.901680 | $0.158447 | 97.32% | $0.793966 | $0.027685 | 96.51% |

shadow 的长父线程一直用 astra 读累积上下文，费用随父 input 增长；live 的父线程在绝大多数样本中也被 Jev 判为 luna，所以本实验不是“astra 父协调 + luna 子任务”的固定对照，而是完整 shadow/live 路由策略对照。

## Jev 判断和真实模型

人工预期三个 docstring 子任务都是 luna。

- `live_none`：27/27 子线程都选 luna，置信度 0.70–0.97。
- `live_all` 的 80k 和 150k：54/54 子线程都选 luna，置信度 0.90–0.97。
- `live_all` 的 30k：6/9 子线程实际 luna；某次重复中，Jev 对三个子任务给出 0.22/0.40/0.46，前一个原始选 sol，后两个原始选 luna 但因低于 0.5 门槛回退 sol。这使该次费用从另两次的 $0.042/$0.064 跳到 $0.891。
- shadow 的 would 子决策全是 luna，实际上游仍是 astra。

真实模型只以 SSE `response.completed.response.model` 为准：

| 设置 | 请求 | completed 模型计数 | input / cached / output token |
|---|---:|---|---|
| shadow_all | 351 | astra 351 | 18,949,357 / 17,705,472 / 25,886 |
| live_all | 539 | luna 495，sol 43，缺 1 | 27,862,076 / 26,592,768 / 82,054 |
| live_none | 576 | luna 576 | 26,517,885 / 25,041,152 / 99,401 |

live 的请求和输出 token 更多，但 luna 价格远低于 astra。这也说明 none 节省一次首请求 input 不保证整个子线程总 token 更少。

## 墙钟和运行可靠性

三档墙钟中位数没有稳定的 none 优势：30k 为 shadow/live_all/live_none = 176.8/270.8/219.6s，80k 为 239.1/248.0/220.5s，150k 为 396.8/419.0/328.5s。这包含父 agent 读 fixture、Jev 决策、三子线程执行和父汇总的全部时间。

为取得 27 个有效样本，共执行 34 次 attempt：7 次被当作基础设施失败重跑，其中 5 次是某个子线程 `jev_error:URLError`，2 次出现 status 0/未完成流。所有失败 attempt 都保留在 `attempts.jsonl`，没有计入有效格汇总。

T2 修复后的 T1 有效数据共 1,466 个请求，1,465 个有 completed。唯一缺失发生在 30k/live_all/repeat-1 的 `docstring_policy` 工具续跑，HTTP status 200；T1 没有开 raw debug 哨兵，因此不能在“上游 EOF 无 completed”和“上游 read 异常”之间进一步分类。这不是 T2 已修复的“客户端断开就不再读上游”路径，但表明费用数据仍需保留缺失标记。

## 这个结果能说明什么、不能说明什么

能说明：

- 在 Codex CLI 0.155.1 上，对“父线程通过大量文件工具输出累积上下文，然后委托与这些输出无关的机械任务”，`fork_turns=all` 没有把父上下文全量计入子首请求。
- 在约 30k、80k、150k 三档上，`live_all` 的子首 token、缓存命中和子费用都没有随父上下文恶化，也没有出现费用交叉点。
- `fork_turns=none` 真实减少了约 5.6k 子首 input，且这组独立委托的通过率没有下降；但整线程费用没有稳定下降。
- 当前证据支持保留 `fork_turns=all` 默认，不要为冷读恐惧全局安装 none 钩子。

不能说明：

- 不能推广到“长上下文由大段用户消息、父 agent 文本输出或与子任务强相关证据构成”的情形；本次长上下文主要是 function-call output，很可能正是 fork 未全量继承的部分。
- 不能证明 none 对需要父历史才能完成的子任务没有质量代价；三个 docstring 任务本身自包含。
- 不能证明 wall time 会按同样比例改善；luna@max 的请求/输出数更多，且本阶段依约没有调 effort。
- 不能把 95%–97% 节省全部归功于“子 agent 分档”；Jev 也将本实验的机械父任务选为 luna，而 shadow 父线程全程 astra。
- 不能声称费用完全无缺失；1,466 个有效请求中仍有 1 条未分类的 completed 缺失，已明确标注为下界。
